# 校准 JSON 功能测试说明

本说明对应 `test/test_calibration_store/test_main.cpp`，解释测试流程、断言含义，以及它与实机重启验证的区别。

## 相关文件

- `test/test_calibration_store/test_main.cpp`：Unity 功能测试。
- `include/calibration_store.h`：声明存储模块对外提供的函数。
- `src/calibration_store.cpp`：生成、保存、读取 JSON，并检查结构。
- `src/main.cpp`：正常固件每次启动时创建一个随机名称的 JSON，并扫描根目录输出文件清单。

## 测试按什么顺序执行

### 1. 准备环境和文档

`calibration_store::begin()` 挂载 LittleFS，断言要求挂载成功。`DynamicJsonDocument document(4096)` 在堆上分配 JSON 文档空间；`created` 用来接收本次是否新建文件的结果。

接着调用 `loadOrCreateTestCalibration(document, created)`：本次运行路径为空时，存储模块选取一个尚未使用的随机文件名；随后生成示例 JSON、写入该路径，再读回检查。断言要求整个过程返回成功。测试没有断言 `created`，因为它在当前实现中始终表示本次创建新文件。

### 2. 写入后读取

```cpp
TEST_ASSERT_TRUE(calibration_store::saveTestCalibration());
TEST_ASSERT_TRUE(calibration_store::loadTestCalibration(document));
```

测试先把已知示例 JSON 写入本次运行分配的测试文件，再读回验证。每次启动会分配新的随机文件名，并保留根目录里的旧文件；`saveTestCalibration()` 只会写入当前运行对应的路径。

### 3. 检查内容结构

测试断言 `magic` 等于 `PPC1_REF_V1`、`version` 等于 `1`，并要求 `temperature_c`、`config`、`points`、`summary`、`fit_rules`、`approval` 是 JSON 对象。

数组长度也会检查：`config.target_rpms` 是 6 项；`points` 中的 `load_index`、`actual_rpm_avg`、`delta_pressure_bar` 和 `flow_mlmin` 各是 24 项。`.as<JsonArrayConst>().size()` 是按只读数组取得元素数。这里验证字段类型和数组长度，**不验证每个示例数值的物理精度**。

### 4. 再读一次文件

测试建立另一个 `DynamicJsonDocument reloaded(4096)`，调用 `loadTestCalibration(reloaded)`，并再次检查 JSON 标识和 24 项数组。这证明写入完成后文件可以再次读取，不只是内存中的对象有效。

### 5. Unity 入口

`setup()` 中的 `UNITY_BEGIN()` 初始化测试框架，`RUN_TEST(...)` 执行上述函数，`UNITY_END()` 输出测试结果；`loop()` 为空。可在项目目录运行：

```sh
pio test -e rymcu-esp32-s3-devkitc-1
```

查看 PlatformIO 串口输出中的 Unity 测试汇总。

## 与断电重启验证的区别

Unity 测试在**同一次测试程序运行中**写入并读取文件，没有主动断电或重启，因此它自身不证明跨启动持久化。正常固件此版本每次启动会创建一个新随机文件。成功写入后会扫描 LittleFS 根目录，串口列出**所有根目录文件**的文件名和长度（字节）；多次启动后，清单应保留先前文件，并新增本次文件。

本测试只使用测试生成的 JSON；不检查文件损坏、空间不足、断电中断或真实校准精度等情形。旧文件会保留，因此多次重启会持续增加占用的 LittleFS 空间。
